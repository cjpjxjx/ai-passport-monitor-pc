# 音画同步专题交接

本文档描述当前音画对齐方案的机制、已知缺陷与待验证项，供后续专题优化接手。已实测、读代码推断、未知三类信息分开标注。

## 目标与约束

- 观看者感知的音画同步；人对声音早于画面比声音晚于画面更敏感，误差应偏向画面略早一侧。
- 文件播放接受起播延迟、不接受丢帧；桌面捕捉优先低延迟，起播丢帧可接受。
- 目标 30 fps 不降级。
- 协议改动固件与 PC 端同步（`main/av_protocol.*` 与 `server/protocol.py`）；不写测试；参考项目只读。

## 当前机制

数据流：`ffmpeg 画面 / 音频两路回环 TCP` → `PC 读取线程入队` → `发送循环` → `设备接收任务` → `设备音频任务 / 画面任务`。

### PC 端（`server/live.py`、`server/tv_server.py`）

- 画面与音频由 ffmpeg 分别输出到两个本机 TCP 端口，读取线程各自入队，发送端按到达顺序发送，不按内容时间配对。没有音频轨的源（无音轨文件、不带 `--audio` 的桌面捕捉）只发画面，CONFIG 不声明音频，设备不建音频时钟。
- 音频块 40 ms，16 kHz 单声道 ADPCM。音频时间戳 = 已发块数 × 40 ms。
- 音频发送节奏：首块发出时刻为锚点，之后最多领先实时 `AUDIO_AHEAD_MS`。
- 画面延后：带音频轨的源，画面在读取线程收到后再等 `AV_LEAD_MS` 才允许发送（`pop_video`）。无音频轨的源不延后。`AV_LEAD_MS` 是固定常量，可用 `TV_AV_LEAD_MS` 覆盖。
- 画面时间戳：带音频轨时 = 发送时刻已发音频的位置（`_send_frame`），否则 = 帧序号乘帧间隔；严格递增，不含画面自身的内容时间。
- 文件源不丢内容：队列满时阻塞读取，起播成批到达的帧按帧间隔顺延；桌面捕捉队列满丢旧帧，到期积压超过 `MAX_DUE_FRAMES` 跳到最新。

### 设备端（`main/av_player.c`）

- 画面到达即画，不等待、不按时间戳排程（`video_task` 注释说明：等待会占住接收环，导致接收停顿与音频欠载）。
- 画面唯一的时间检查：音频时钟已就绪且 `estimated_pts() - 画面时间戳 > 100 ms` 时丢弃该帧；时钟未就绪时直接画。
- 音频时钟：首次向 I2S 写入时取 `clock_us = 写入时刻 + DMA_ESTIMATE_MS`，之后按已提交采样数推进，静音补洞不计入节目位置。`DMA_ESTIMATE_MS` 是估算，代码注释写明不是 DMA 实测。
- 音频起播门槛 `AUDIO_START_CHUNKS`；音频队列接近满时暂停读取，由 TCP 背压把 PC 发送速度拉到 I2S 速度。
- 音频队列取空时补静音，持续超过 `AUDIO_SILENCE_MAX_MS` 才判会话失败。

## 已实测

- 设备起播耗时（`AUDIO_START ready_ms`，从 CONFIG 就绪到首次写入 I2S）：去掉 DMA 静音冲洗后 212 ms（队列 4 块）；保留冲洗时 452 ms（队列 8 块）。各 1 次采样。
- 起播丢帧：改造前 PC 丢 9 至 12 帧、设备丢 16 帧；文件源无损改造后设备 `dropped=0`、`late=0`，PC `dropped_video=0`。
- ffmpeg 起播时一次吐出约 15 帧（约 0.5 秒内容），之后按实时节拍到达。`-probesize` 与 `-analyzeduration` 不改变该突发。
- 以上均未涉及实际音画相对偏差。

## 读代码推断（未实测）

- 设备端对画面只丢不等，对齐完全依赖 PC 端固定延后，没有闭环。
- 画面时间戳反映的是"发送时刻的已发音频位置"，而设备时钟是"已播放位置"，两者差约等于设备队列深度加 DMA 缓冲。稳态下画面时间戳通常领先设备时钟，100 ms 检查很少触发，它检测的是发送端滞后，不是内容层面的音画偏差。
- 声音从到达设备到出声的时延由设备队列深度与 DMA 缓冲决定，推测在 170 ms 以上；画面从到达到显示的时延未测。
- `AV_LEAD_MS=250` 来自听感与代码估算，未测量。若实际声音时延小于 250 ms，则声音早于画面，落在人最敏感的一侧。

## 已知缺陷

1. 延后量是写死的开环常量，符号（声音早或晚）与大小都没有实测依据。
2. 音频、画面不按内容时间配对：二者各自从 ffmpeg 到达的先后决定起播相对偏移；音频块丢失会使时间戳压缩（累计块数不含丢掉的块），文件源无损后不再丢，桌面捕捉仍会。
3. 画面时间戳不携带内容时间，设备无从判断画面与声音在内容上是否同时。
4. 三个时钟互相独立：ffmpeg 的实时读入、PC 单调时钟、设备 I2S 晶振。长时间漂移未量化，也没有校正机制。
5. 延后量不随传输方式（USB 与 Wi-Fi）、设备队列实际深度、固件缓冲参数变化，修改任一项都需重调。
6. 桌面捕捉的画面（ddagrab）与环回声音（WASAPI）也是独立时钟，同样无配对；`--audio` 时沿用 250 ms 延后，与"桌面捕捉优先低延迟"的目标冲突。
7. 误差方向没有被设计：现有常量没有"宁可画面略早"的偏置。

## 待验证项

按优先级：

1. **测实际音画偏差**：生成"画面闪一下同时响一声"的测试视频，手机高帧率同时拍屏幕与扬声器，统计帧差。分别测 Wi-Fi 与 USB、有声与无声源、起播阶段与 10 分钟后。
2. **设备端埋点**：画面绘制时刻记录 `estimated_pts()` 与画面时间戳之差，以及音频队列深度，量出稳态下的设备时延。
3. **量化漂移**：长时间播放，对比起播与 N 分钟后的偏差。
4. **确定验收标准**：声音早与声音晚各允许的最大偏差，待定。

## 候选方向（均未决定）

- **A. 实测标定常量**：按传输方式分别测出声音时延，延后量取略小于测值，使误差偏向画面略早。改动最小，仍是开环，不解决漂移与配对问题。
- **B. PC 端内容时间配对**：用 ffmpeg 输出的时间戳（解码器自身 PTS）把画面与音频放到同一条内容时间轴上，再统一计算发送时刻。
- **C. 画面带内容时间、设备按音频时钟排程**：画面时间戳改为内容时间，设备把早到的画面保留到时钟到达再画。与现行"到达即画"的刻意决策冲突，需评估接收环容量（`AV_VIDEO_RING_BYTES`）与堆余量。协议语义变化，两端同步修改。
- **D. 设备向 PC 反馈播放位置**：新增控制包上报已播放位置，PC 闭环调整延后量，可校正漂移。协议改动，控制包上限 1024 字节。
- **E. 按源类型区分策略**：文件源追求同步，桌面捕捉默认不延后画面（画面早、声音晚，落在人较不敏感的一侧），需要同步时再开启。

组合方式建议由实测结果决定：若偏差稳定且漂移小，A 加 E 即可；若漂移明显或起播偏移不可控，再考虑 B 或 C 加 D。
